## 1. Decision summary

v0.1.1 is a successor to the bounded v0.1 iteration engine. Its purpose is to raise harness-iteration flexibility
substantially — plugin-shaped development, bounded add/modify/remove over a real candidate tree, governed expansion
of DSH attachment surfaces, and iteration that is actually driven by trajectory analysis — without moving any part
of the original design direction: the frozen TCB, evidence isolation, fail-closed admission and the claim
vocabulary all stay exactly where v0.1 put them.

Concretely, v0.1.1 replaces the current single-file `sourceDiff` proposal with a content-addressed child-tree
protocol, gives the disposable proposer read/search/edit tools over a real label-filtered evidence export, loads
the selected parent candidate in `propose` mode through the real Cordis Loader, and adds two feedback channels that
make iteration cumulative rather than one-shot: trusted mechanism-outcome records and declarative capability
requests.

The trusted boundary does not move:

```text
immutable DSH + model route + benchmark + verifier + controller policy
                              |
                    trusted export and builder
                              |
            one-shot proposer and candidate processes
                              |
               evolvable candidate source package
```

The proposer may author multiple production modules, candidate-owned tests, bounded data fixtures and descriptive
metadata. It may not author package identity, dependencies, runtime rows, model configuration, evaluation policy,
budgets or evidence labels. The trusted host derives the actual tree diff, hashes every output byte and admits only
an immutable artifact that passes the complete build and Loader pipeline.

The accepted engineering capability is:

```text
claimStatus: AUTONOMOUS_PLUGIN_DEVELOPMENT_VERIFIED
capability: AUTONOMOUS_PLUGIN_DEVELOPMENT_VERIFIED
DSH_UPSTREAM_UNMODIFIED
SEALED_NOT_ACCESSED
BENCHMARK_IMPROVEMENT_NOT_CLAIMED
```

`AUTONOMOUS_PLUGIN_DEVELOPMENT_VERIFIED` is a scoped capability receipt, not a new benchmark status and not a
replacement for the claim vocabulary in [`specs/00` §10](../specs/00-product-contract.md#10-claim-vocabulary).

## 2. Flexibility model

All added flexibility lives on three axes, and every axis has exactly one change speed. Anything not listed here
keeps its v0.1 rigidity.

| Axis                   | What can vary                                                                         | Who decides                 | Change speed                                       |
| ---------------------- | ------------------------------------------------------------------------------------- | --------------------------- | -------------------------------------------------- |
| Source surface         | files added/modified/removed inside the declared candidate tree; internal composition | proposer                    | every generation, within frozen containment limits |
| DSH attachment surface | which exact catalog capabilities are enabled for candidates                           | trusted operator + fixtures | per run lineage, at manifest freeze                |
| Contract envelope      | ownership matrix, containment limits, tier semantics, TCB boundary                    | ADR + protocol bump         | per protocol version, with a fresh lineage         |

Two consequences are deliberate:

1. A proposer can restructure its candidate freely inside axis one on every generation — new modules, removed
   modules, internal plugin composition, new tests — with no human in the loop and no protocol event.
2. A proposer can _request_ axis-two changes (new exact capabilities) as declarative data, but nothing a candidate
   or proposer writes can widen the current run. Requests are harvested between lineages and go through fixtures
   and manifest re-freeze; envelope changes additionally require an ADR. This is the governed path from "the model
   wants a new attachment surface" to "the next lineage has it", replacing ad-hoc hand edits of trusted config.

## 4. Goals and non-goals

### 4.1 Goals

1. Let the proposer add, modify and remove bounded files in its declared candidate source package without human
   source edits.
2. Make each child traceable from immutable `DEV_OBSERVED` evidence, through an explicit analysis artifact, to an
   actual production diff and tests.
3. Let improvements in a parent's `propose` behavior affect the next generation by loading that exact parent, not a
   hard-coded baseline substitute.
4. Preserve canonical identity, deterministic builds, real Loader lifecycle checks, one-shot isolation and
   crash-safe exactly-once recovery.
5. Expand DSH attachment surfaces only through a content-addressed capability catalog frozen before the run, with a
   repeatable request → fixture → re-freeze lifecycle between lineages.
6. Let candidates structure themselves as composed internal plugins under one Loader row, so mechanism-level
   add/remove/modify is a normal file operation instead of a monolithic `index.ts` rewrite.
7. Make iteration cumulative: a generation can see, through trusted mechanically-derived outcome records, whether
   an ancestor's hypothesis was followed by the predicted observable change, and must reconcile against that before
   re-proposing the same mechanism.

### 4.2 Non-goals

- Modifying or forking `deepseek-harness/`, `harbor/`, `tb/` or their pinned checkouts.
- Allowing arbitrary dependencies, lifecycle scripts, native modules, direct Node filesystem/process/network APIs or
  dynamic code loading.
- Giving candidates or proposers credentials, verifier internals, guard/sealed material, controller state or a
  writable evidence store.
- Letting a candidate, proposal or capability request widen the running lineage's catalog, limits or policy.
- Training model weights on trajectories or treating in-context analysis as fine-tuning.
- Claiming a hypothesis is true merely because its generated test, compilation, Loader boot or one task run is green.

## 5. Trust boundary and end-to-end flow

One generation is a durable sequence of trusted and untrusted steps:

```text
freeze parent + evidence export + capability catalog + child slots
  -> launch one-shot proposer with the exact parent in propose mode
  -> proposer reads raw evidence and edits only its preassigned child tree
  -> trusted host derives actual operations and publishes immutable source objects
  -> trusted admission builds, scans, tests, loads, unloads and packs the child
  -> Harbor evaluates an admitted capsule on a preselected development task
  -> normalizer publishes raw and normalized DEV_OBSERVED evidence
  -> trusted controller derives the child's mechanism-outcome record
  -> a later generation receives a new immutable filtered export
```

Candidate code is never imported into the long-running controller. Proposal and evaluation each use a fresh OS
process/container, and candidate code reaches DSH only through a real Loader. `node:vm`, manual `ctx.plugin()` and
the current process's TypeScript import graph are not security or admission boundaries.

## 6. Candidate tree and file ownership

### 6.1 Canonical proposer view

The trusted host creates each child slot from the exact canonical parent before the proposer starts:

```text
/work/children/<reserved-proposal-id>/
├── tree/
│   ├── candidate.json
│   ├── package.json
│   ├── cordis.patch.yml
│   ├── src/
│   │   ├── index.ts             # single Loader entry, mandatory
│   │   └── **/*.ts              # nested candidate modules and components
│   ├── tests/**/*.spec.ts
│   ├── fixtures/**/*.json
│   └── README.md
├── analysis.json
└── proposal.json
```

The tree starts as a no-link, byte-for-byte materialization of the canonical parent. A child is therefore a complete
tree, not an archive supplied by the model and not a patch interpreted against an ambient checkout. Arbitrary nested
directories under `src/`, `tests/` and `fixtures/` are allowed within the containment limits; there is no privileged
`components/` name.

### 6.2 Candidate-internal plugin composition

Plugin-shaped development happens inside the bundle, under one unchanged Loader surface:

- `cordis.patch.yml` stays a frozen template and inserts exactly one candidate row; `src/index.ts` remains the only
  Loader entry.
- The candidate MAY structure behavior as nested namespace-form components (`name`/`inject`/`Config`/`apply`,
  no default export) anywhere under `src/**`, statically imported and mounted from `apply` through the candidate's
  own scoped Context, so every component Fiber is a descendant of the candidate root Fiber.
- Adding, removing or rewiring a component is then an ordinary tree operation covered by the declared-operations
  protocol — no manifest surgery and no Loader-row change.
- Each component's `inject` set must resolve from catalog-allowed services only; composition can never reach a
  capability the catalog denies to the candidate as a whole.
- Dynamic `import()`, registering additional Loader rows, HMR, and mounting anything outside the candidate's own
  static import graph remain rejected by the existing policy scan.
- The admission Loader stage records the nested component inventory (component names, injected services, registered
  tools/listeners) as part of the expected surface inventory, and unload quiescence is measured at the candidate
  root: disposing the root Fiber must return the full inventory to baseline.

### 6.3 Ownership matrix

| Path or field                                       | Proposer access   | Trusted rule                                                           |
| --------------------------------------------------- | ----------------- | ---------------------------------------------------------------------- |
| `src/**/*.ts`                                       | add/modify/remove | `src/index.ts` remains mandatory; TypeScript and import policies apply |
| `tests/**/*.spec.ts`                                | add/modify/remove | candidate-owned tests are untrusted supporting evidence                |
| `fixtures/**/*.json`                                | add/modify/remove | data-only, schema-valid and byte-bounded                               |
| `README.md`                                         | add/modify/remove | never executable and never an authority source                         |
| candidate-owned fields in `candidate.json`          | modify            | schema-v2 JSON Pointer allowlist only                                  |
| `package.json`, `cordis.patch.yml`, compiler config | read only         | exact frozen template; build tree is materialized by the builder       |
| derived IDs, hashes, SBOM, provenance, signatures   | absent/read only  | written only to trusted build/capsule manifests                        |

The schema-v2 candidate manifest must separate proposer-authored behavior intent from builder-derived identity. A
derived candidate ID must not be embedded in the bytes used to derive that same ID. Runtime package names and Loader
rows are materialized in a separate build tree from frozen templates and are bound to the canonical source digest by
the build manifest.

The schema-v2 JSON Pointer allowlist for `candidate.json` covers only behavior intent: the proposal block
(hypothesis, target failure modes, expected behavior change, regression risks, touched surfaces), declared runtime
intent (`requiredServices`, `optionalServices`, `newToolNames`, `supportsModes` — each validated against the frozen
catalog) and the test assertion lists. Identity, provenance and receipt fields are builder-owned.

### 6.4 Default containment limits

| Limit                      | Default |
| -------------------------- | ------: |
| total canonical files      |      25 |
| canonical source bytes     |   1 MiB |
| changed lines from parent  |   5,000 |
| candidate-owned test files |      10 |
| total fixture bytes        | 256 KiB |
| new candidate dependencies |       0 |

Paths are normalized POSIX-relative UTF-8. The host rejects symlinks, hardlinks, devices, sockets, absolute or `..`
paths, Unicode/case collisions, undeclared outputs, NUL bytes and limit overruns. Changing any limit requires an ADR,
protocol-version bump and fresh lineage; a proposal cannot request an exception for the current run — it can only
record a capability request under §10.4.

## 7. Evidence export and trajectory citations

### 7.1 Export contents

The proposer receives one action-scoped, read-only export containing only `PUBLIC_SPEC` and `DEV_OBSERVED` objects.
The export is produced by the trusted object store before sandbox launch and includes a content-addressed manifest,
Merkle root, source state hash and canary-absence receipt.

| Evidence class                    | Required use                                                 |
| --------------------------------- | ------------------------------------------------------------ |
| normalized trial record           | establish pass/fail/invalid outcome and failure class        |
| ATIF trajectory                   | locate model/tool behavior and task-visible errors           |
| ACP events and summary            | establish turns, stop reason and settlement                  |
| DSH session events                | establish effective prompt/tool/event behavior               |
| ancestor source and semantic diff | identify mechanisms already present                          |
| ancestor analysis objects         | restate open failure clusters and prior hypotheses           |
| mechanism-outcome records         | reconcile a new hypothesis with what ancestors already tried |
| proposal/build rejection receipt  | avoid repeating a rejected implementation                    |
| capability-request ledger         | avoid re-requesting what is already recorded or denied       |
| archive catalog                   | navigate lineage and `DEV_OBSERVED`-only statistics          |

The proposer never receives guard/sealed identities, results or aggregates; verifier source; reward internals;
credentials; provider bodies; controller journal/state; budget internals; or concurrent proposer outputs. A journal
event hash may be recorded in trusted provenance, but raw controller journal records are not proposal inputs.

### 7.2 Resolvable citations

A free-form `evidenceRefs: string[]` is insufficient. Schema v2 uses structured citations:

```json
{
  "objectDigest": "sha256:<64-hex>",
  "mediaType": "application/vnd.dsh-rsi.atif+json",
  "locator": { "kind": "json-pointer", "value": "/events/12" },
  "observation": "The agent stopped after the first retryable tool error."
}
```

The validator must prove that the digest exists in the bound export manifest, its immutable label is allowed by the
export, its media type matches and the locator resolves within the hashed bytes. Every failure cluster and child
hypothesis must include at least one `DEV_OBSERVED` trajectory citation and its matching normalized outcome;
`PUBLIC_SPEC` citations may support contracts or source context but cannot establish an observed failure. For JSONL,
the locator is a one-based line range; for JSON, it is an RFC 6901 JSON Pointer. Arbitrary filesystem paths, URLs and
unexported journal references are rejected.

Resolution proves provenance and location, not semantic truth. The proposer's causal interpretation remains an
untrusted hypothesis until supported by trusted replay or benchmark evidence.

### 7.3 Durable analysis artifact

Each proposal stores a separate, schema-valid analysis object containing:

- failure clusters named by mechanism rather than task identity, each with a proposer-chosen stable slug;
- citations supporting each cluster;
- existing ancestor/donor mechanisms considered;
- for every cluster that any exported ancestor analysis also targeted: a citation of that ancestor analysis and of
  its mechanism-outcome record, plus a stated position (mechanism confirmed insufficient, superseded, or retried
  with a distinct change);
- the selected cluster and falsifiable hypothesis;
- expected behavior change, preservation requirements and regression risks.

The analysis object, raw proposal transcript and tool trace are content-addressed before build. A later generation
may cite them only through a new legal export. Retention is evidence lineage; it is not permission to relabel or
expose guard/sealed data.

Cluster slugs are untrusted continuity hints, not identities: trusted code never merges or scores clusters by slug,
it only preserves the citation chain that lets a later proposer reconstruct which mechanisms were already tried.

### 7.4 Mechanism-outcome records

After a child's development evaluation settles, the trusted controller derives one mechanism-outcome record per
child from normalized `DEV_OBSERVED` trials only. It binds the proposal digest, hypothesis digest, child candidate
digest, target cluster slug, the frozen target task handle and the trial refs, and reports a mechanically derived
status:

```text
TARGET_IMPROVED        # frozen baseline-failed target task passed under the child
TARGET_UNCHANGED       # target task still failed under the child
TARGET_NOT_MEASURED    # no completed target trial (budget, infra, rejection)
PRESERVATION_REGRESSED # a preregistered preservation trial that passed before failed under the child
INVALID_TRIALS         # the target trial normalized to invalid; fail closed
```

The record carries the trial counts it is derived from; a single-trial status is labeled as such and is a noisy
observable, not a causal verdict. Semantic interpretation — whether the mechanism worked — remains the next
proposer's untrusted job. The record is labeled `DEV_OBSERVED`, never aggregates guard/sealed data, and enters later
generations only through a legal export.

## 8. Proposer runtime contract

The proposer is an ordinary DSH agent inside a one-shot Bubblewrap/container boundary. The exact selected parent
bundle, extracted from its immutable capsule, is loaded through the real Cordis Loader with `mode=propose`; a fixed
import of the baseline candidate is a contract failure.

The TCB supplies bounded audited tools, not direct Node APIs:

| Tool class        | Read scope                                           | Write/execute scope                 |
| ----------------- | ---------------------------------------------------- | ----------------------------------- |
| list/read/search  | parent, archive, evidence, contracts, own child slot | no writes                           |
| write/edit/remove | own preassigned child `tree/` only                   | no links or rename escape           |
| test/typecheck    | own child tree plus pinned read-only toolchain       | no network; bounded CPU/time/output |
| finish            | own `proposal.json`                                  | validates schema before clean exit  |

The initial prompt contains goals, budgets, mount indexes and the output contract, not the full trajectories. The
agent uses tools to inspect raw evidence on demand. Every tool call is retained. Network is limited to the fixed
model gateway; the sandbox has no credentials, host home, controller socket, Docker socket or sibling child slot.

The controller preassigns proposal IDs and output directories before model launch. Parser fallback IDs, wall-clock
IDs and `Math.random()` are forbidden because they break deterministic replay and idempotency.

## 9. Proposal and trusted materialization protocol

### 9.1 Schema-v2 envelope

The proposer edits the child tree directly and writes metadata to the fixed `analysis.json` and `proposal.json`
paths. File bytes and analysis bytes do not appear as model-asserted object references:

```json
{
  "schemaVersion": 2,
  "proposalId": "<controller-reserved-id>",
  "canonicalParentDigest": "sha256:<64-hex>",
  "evidenceExport": {
    "manifestDigest": "sha256:<64-hex>",
    "merkleRoot": "sha256:<64-hex>"
  },
  "donorCandidates": [],
  "analysisPath": "analysis.json",
  "hypothesis": "One falsifiable mechanism-level hypothesis",
  "evidenceCitations": [
    {
      "objectDigest": "sha256:<64-hex>",
      "mediaType": "application/vnd.dsh-rsi.atif+json",
      "locator": { "kind": "json-pointer", "value": "/events/12" },
      "observation": "The agent stopped after the first retryable tool error."
    }
  ],
  "declaredOperations": [
    { "op": "add", "path": "src/retry/bounded-retry.ts" },
    { "op": "modify", "path": "src/index.ts" }
  ],
  "mechanismAssertions": ["one transient failure causes at most one retry"],
  "preservationAssertions": ["successful first calls are never repeated"],
  "capabilityRequests": [
    {
      "capability": "tools/pre-execute",
      "tier": "T2",
      "motivation": "clamp duplicate tool dispatch before execution",
      "evidenceCitations": []
    }
  ]
}
```

`proposalId`, parent digest, export binding and the literal analysis path must exactly equal the durable reservation.
The child retains one canonical parent; borrowed mechanisms use donor provenance and never create a second parent
edge.

`capabilityRequests` is optional, bounded (default at most 3 entries), schema-valid data. It has zero effect on the
current run: it cannot change the catalog, admission, limits or scoring, and an invalid request rejects only itself,
not the proposal. Its lifecycle is defined in §10.4.

### 9.2 Trusted materializer

After the proposer exits, the host performs the following without executing candidate code:

1. Walk parent and child with `lstat`, no symlink following, and validate paths/types/limits.
2. Derive the exact add/modify/remove set from immutable parent bytes and child bytes.
3. Require exact equality between derived and declared operations; reject missing or extra output.
4. Resolve every evidence citation against the bound export and verify analysis/proposal schemas.
5. Canonicalize the full source tree, publish each object no-replace and write a materialization receipt.

The receipt binds reservation ID, parent/source/export/analysis/transcript digests, the independently persisted
proposer resource-receipt digest, derived operations, capability catalog, retained capability requests and proposer
usage. Cache adoption and audit replay the resource receipt's frozen policy/mount/peak/event/completion semantics as
well as its digest. The model cannot assert a trusted content digest; all hashes are recomputed after the sandbox
exits.

## 10. DSH capability catalog

### 10.1 Frozen exact catalog

Tier names are policy groupings only. The run manifest freezes a generated catalog of exact DSH package exports,
service names, event names, event modes, TypeScript signatures and lifecycle tests from the pinned DSH commit. The
catalog digest is part of candidate admission and run identity; a broad string such as `agent/*` is never an
executable allowlist.

| Tier                | Default policy                | Example exact capabilities                                                                                                                         |
| ------------------- | ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| T0 prompt           | enabled                       | candidate-scoped `systemPrompt.section`                                                                                                            |
| T1 observe/compose  | enabled after fixtures pass   | emit-only `tools/result`; `session/event`; bounded per-session memory; candidate-internal nested components (§6.2)                                 |
| T2 intercept/create | disabled unless preregistered | `tools/pre-execute`/`execute`/`post-execute` waterfalls, `agent/request-error`, candidate-owned tools, approved subagent seams                     |
| T3 privileged       | always forbidden              | `agent/request`, raw LLM adapter, Loader/HMR, credentials, controller/budget/evidence/sealed services, process lifecycle, direct fs/net/subprocess |

The distinction is semantic: in the pinned DSH source, `tools/result` is an emit observer, while
`tools/pre-execute`, `tools/execute` and `tools/post-execute` are waterfall middleware that must preserve `next()` and
cancellation contracts. `agent/request` can alter effective model-call configuration and therefore remains TCB-only.

### 10.2 Enablement fixtures

Every enabled exact capability requires an accept fixture, misuse/negative fixture, scoped visibility check and
Loader unload/quiescence check before the run starts. Unknown imports, services, events or tool names are
`REJECTED_POLICY`.

### 10.3 Two-speed catalog change rule

The catalog is the governed flexibility axis, and it moves at exactly two speeds:

- **Per lineage, no ADR:** enabling or disabling an exact capability _within its existing tier semantics_ — for
  example preregistering a specific T2 waterfall for the next run — happens at run-manifest freeze, after its §10.2
  fixtures pass. The new catalog digest creates a fresh lineage; results across catalog digests are not merged.
- **Per protocol version, ADR required:** moving a capability between tiers, changing tier default policy, changing
  the ownership matrix or containment limits, or touching anything in T3. These follow
  [`specs/07` §13](../specs/07-implementation-plan.md#13-change-control) in full.

Nothing changes the catalog mid-run. The effective catalog for every admitted child is the digest bound into its
admission receipt.

### 10.4 Capability-request lifecycle

Requests are the auditable bridge between what proposers want and what a future lineage enables:

```text
generation N: proposer emits bounded capabilityRequests (data only, no effect)
  -> materializer retains them in the receipt and the capability-request ledger
  -> lineage end: trusted aggregation report (dedup by exact capability, cite counts, motivations)
  -> trusted review selects zero or more for enablement
  -> §10.2 fixtures are authored and pass
  -> same-tier enablement: next run manifest freezes catalog v(n+1)
  -> tier/ownership/limit change: ADR + protocol bump + fresh lineage
```

Denied or ignored requests stay in the ledger with their disposition, and the ledger is part of later legal exports
so proposers stop re-requesting settled items. A request is never a promise, never consumes a proposal attempt, and
never weakens the current run.

## 11. Trusted admission pipeline

Candidate-owned tests are untrusted supporting evidence: they may be wrong, vacuous, malicious or resource-hungry.
They run in a networkless one-shot build sandbox before trusted tests and can never waive a trusted failure.

| Stage                       | Required receipt or failure                                                     |
| --------------------------- | ------------------------------------------------------------------------------- |
| containment and actual diff | path/type/limit receipt; exact parent and declared-operation match              |
| schema and template         | proposal, analysis, candidate and frozen builder-template validation            |
| policy and dependency graph | AST/resolved-import/capability/secret/task-fingerprint report                   |
| candidate tests             | bounded mechanism and preservation test result with timeout/process drain       |
| deterministic build         | two clean builds with byte-identical emitted trees                              |
| real Loader lifecycle       | namespace load, expected surface and component inventory, unload and quiescence |
| fixed replay                | both modes, event ordering, tool schemas and bounded termination                |
| immutable capsule           | offline boot, SBOM, provenance, sums and no source-checkout dependency          |
| resource completion         | limits, target/supervisor PID isolation, complete peaks/events, zero exit       |
| final admission             | one signed/content-addressed receipt binding all prior artifacts                |

Current immutable capsules use manifest schema 2 and `dsh-capsule-tree-v2`: the exact directory set, normalized
evaluated executable mode, regular-file bytes and symlink targets are all checksum-bound. Entry names must be strict
UTF-8 without control characters, checksum control text must be strict UTF-8, literal symlink-target bytes are hashed
without replacement decoding, and regular files/symlinks must be single-link inodes. Fresh admission and
stable-build resume revalidate the live v2 tree, its offline-sums receipt and `capsuleHash`; schema-1 file/symlink sums
remain labelled predecessor evidence and cannot satisfy a fresh admission, resume or evaluation identity.

The generated production diff must be non-empty. Test-only, comment-only, formatting-only and manifest-only children
are rejected. Passing generated tests does not validate the hypothesis; the report must call it an unconfirmed
mechanism hypothesis unless an independent trusted replay or evaluation supports it.

## 12. Recovery, retries and accounting

The default v0.1.1 engineering demo preserves the v0.1 paid-task envelope:

| Bound                                      |    Default |
| ------------------------------------------ | ---------: |
| admitted children `K`                      |          3 |
| child slots per generation                 |          1 |
| proposal/admission attempts per generation |          3 |
| baseline failure-discovery trials          | at most 12 |
| candidate solver trials                    |          3 |
| total solver trials                        | at most 15 |
| guard/sealed access                        |          0 |

The run manifest also freezes proposer token/USD, output-byte, wall-clock and process-resource limits before the first
proposal. Raising any limit creates a fresh lineage.

Each generation has one durable reservation and at most three distinct proposal/admission attempts. The limit covers
proposal-protocol, materialization, policy, test, build, Loader and capsule rejection together; it is not three
attempts per stage.
Within an attempt, exported worker output is reusable only when a manifest-last execution commit binds the exact
worker/resource/gateway/diagnostic bytes. Before that commit, the trusted exporter fsyncs every child file, the staged
directory tree and each parent-directory rename/removal boundary. Recovery quarantines both pre-commit output and a
committed execution whose installed worker/tree is absent or digest-mismatched, recreates the child slot from the
immutable parent and replays durable gateway request ids. Materialization cache and audit independently verify the
exact wrapper, artifact digest and content-addressed materialization/analysis bytes before reuse. Final audit also
requires a one-to-one inventory between active execution manifests and materializations; explicitly quarantined crash
evidence remains retained but has no authority. Inventory and semantic replay consume the same direct-action scan;
active symlinks, hardlinks and special entries fail closed. The materialization cache itself is published only from a
fsynced staging inode through a no-clobber link and directory fsync. A torn/invalid cache or a post-cache worker/tree
loss is quarantined with its execution before adoption while the durable gateway request store remains replayable.

Deterministic identities include:

```text
proposal = H(run, generation, attempt, parent, export, capability-catalog, proposal-protocol)
build    = H(run, proposal, canonical-source, builder-protocol)
eval     = H(run, candidate, task-handle, split, attempt, eval-protocol)
```

- A completed proposal output is content-addressed before its event commits; resume reuses it and never calls the
  model again.
- A published source/build/capsule is reused by digest; resume does not assign a new candidate ID.
- A deterministic rejection is retained and may be included in the next attempt's legal export.
- A mechanism-outcome record is derived once per settled child by idempotency key; resume never derives a second,
  conflicting record.
- Infrastructure ambiguity is reconciled by idempotency key before retry; it never consumes a replacement attempt
  merely because the controller does not know whether launch happened.
- Three rejected attempts terminate the generation as `NO_ADMISSIBLE_CHILD`; policy and limits remain unchanged.

Proposer tokens/USD, failed builds, rejected attempts and candidate trials all remain in the budget/evidence ledger.
Rejected proposals do not count toward admitted `K`.

## 13. Migration and versioning

Implementation started only after v0.1 Gate 7 had an immutable release commit and acceptance receipt. The following
migration steps were completed on a fresh schema-11 lineage:

1. Write the ADR for candidate-tree identity, exact editable JSON pointers, capability tiers, internal composition
   and v0.1 parent import.
2. Add successor schemas for proposal v2, trajectory analysis, candidate intent, capability requests,
   mechanism-outcome records, materialization and admission receipts; do not mutate v1 schemas in place.
3. Create a fresh v0.1.1 baseline artifact from the accepted v0.1 source through an explicit migration receipt; do
   not inherit v0.1 scores, failure pools or proposal outputs.
4. Start a new config/protocol/run lineage with new evidence exports and tasks frozen before candidate rewards.
5. Keep every v0.1 artifact byte-identical and replayable; never silently rehash or relabel it as v0.1.1.

If the v0.1 release changes any predecessor behavior listed in §3, this design must be re-audited before the ADR is
accepted. The implementation must follow the final release artifact, not this document's historical snapshot.

## 14. v0.1.1 acceptance gates

### V011-A — Contract and containment

- Successor schemas compile and reject unknown fields.
- Add/modify/remove fixtures derive the exact operation set from full trees, including nested directories.
- Traversal, links, collisions, undeclared output, template changes and identity self-reference are rejected.
- Evidence locators resolve only within the bound legal export.
- Exact capability-catalog accept and negative fixtures pass.
- A synthetic `capabilityRequests` entry is retained as data and provably cannot change the effective catalog,
  limits or admission of the current run.

### V011-B — Real trajectory-grounded proposal

- The proposer receives real raw baseline-failure trajectory, ACP and normalized objects through an immutable
  `DEV_OBSERVED` export.
- It uses retained tool calls to inspect those objects and emits a schema-valid analysis with resolvable spans.
- When an exported ancestor analysis targeted the same cluster, the new analysis cites that analysis and its
  mechanism-outcome record and states its position before re-proposing.
- It creates at least one new production module and updates `src/index.ts` to use it.
- The exact selected parent loads in `propose` mode; replacing it with the baseline negative fixture is detected.
- No human edits proposal source between sandbox exit and admission.

### V011-C — Real generated-plugin admission

- Candidate-owned mechanism and preservation tests run in a bounded sandbox.
- Trusted policy, dependency and task-fingerprint scans pass.
- Two clean builds are byte-identical.
- Generated bytes pass real Loader boot/unload and fixed replay in both modes, with the nested component inventory
  recorded and returned to baseline on unload.
- The packed capsule boots offline with complete SBOM/provenance/checksums.

### V011-D — Rejection and crash recovery

- One deterministic invalid child is retained, classified and replaced without weakening policy.
- A real process crash after proposal publication resumes without another model call.
- A separate crash after external evaluation launch resumes without duplicate trial, score or cost.
- A crash between trial settlement and outcome-record derivation resumes to exactly one mechanism-outcome record.
- Full replay and snapshot resume end at the same state hash and lineage.
- Exhausting three attempts reaches `NO_ADMISSIBLE_CHILD` deterministically.

### V011-E — Bounded autonomous iteration

- A fresh development-only `K=3` run admits three unique candidates with lineage depth at least two.
- At least one admitted child contains multiple production source files.
- A depth-2 child's selected hypothesis cites a concrete span from a depth-1 candidate's trial trajectory, its
  normalized outcome and its mechanism-outcome record.
- Every candidate task was frozen from baseline evidence before any candidate reward was visible.
- `sealedAccessCount=0`; no score improvement or champion selection is required.

Only artifacts from all five gates may mint the scoped capability receipt
`AUTONOMOUS_PLUGIN_DEVELOPMENT_VERIFIED`.

## 15. Evidence and claim boundary

The release receipt must bind at least:

| Claim                | Minimum artifact                                                                     |
| -------------------- | ------------------------------------------------------------------------------------ |
| multi-file autonomy  | proposer tool trace, actual tree diff and no-human-edit receipt                      |
| trajectory grounding | export manifest, analysis object and resolvable evidence citations                   |
| cumulative iteration | mechanism-outcome records plus a descendant analysis that reconciles against them    |
| real DSH plugin      | exact-parent proposal Loader receipt plus child boot/unload receipt                  |
| governed flexibility | frozen catalog digest, fixture receipts and a non-widening capability-request ledger |
| recovery             | crash boundary receipts, idempotency mapping and equal replay state hash             |
| bounded safety       | capability catalog, sandbox policy, negative fixtures and canary scan                |

Permitted statement:

> Under the frozen v0.1.1 protocol, the system autonomously inspected development evidence and authored, built,
> loaded, evaluated and iterated bounded multi-file DSH candidate plugins. The run did not access sealed tasks and
> does not establish benchmark improvement, universal usefulness, complete security, leaderboard readiness or SOTA.

The document, schemas, green unit tests, one generated child or a K=3 terminal state alone cannot support that
statement. Raw proposal, build, Loader, Harbor, recovery and evidence-binding artifacts must all exist.

## 16. Completed implementation slice

After the v0.1 prerequisite and ADR were accepted, the implementation completed these slices:

1. Implement proposal schema v2, analysis schema v1, mechanism-outcome schema v1 and a trusted materializer for
   `src/index.ts`, one nested module directory, `tests/**/*.spec.ts`, `candidate.json` and `README.md`.

bounded engineering-capability result; expansion of capability tiers or benchmark search requires a fresh lineage.
